我们着重要关注的是​`MmAllocateIndependentPagesEx`, 该函数的内存申请机制大体如下：

```c
// 该函数在系统空间的非分页部分查找指定数量且连续的未使用的PTE
1. MiReservePtes(&MiSystemPteInfo, (unsigned int)v6);	
// 获取PTE对应的VA
2. Address = (__int64)((_QWORD)PTE << 25) >> 16;
// 构建成有效的PTE
4. MiMakeValidPte((unsigned __int64)PTE, 0, 0xA0000004LL);
// 初始化 Page Color
5. MiInitializePageColorBase\MiGetNextPageColor		
// 根据Size, 每次循环获取一份系统物理页 _MMPFN
6. MiGetSlabPage((__int64)&MiSystemPartition, v14, 0, (__int64 *)0xFFFFFFFFFFFFFFFFLL, 0);
// 初始化 _MMPFN, 就是给PTE挂上PFN
7. MiInitializePfn(0x30 * PFN2 - 0x58000000000LL, PTE, 4, 4);
```

看的出来这种内存申请机制压根没走Pool管理, ​`MmGetPhysicalMemoryRanges`倒是可以获取它的信息.

同样的对于这种内存有诞生出了不少的检测手段, 参考: [https://xz.aliyun.com/news/18995](https://xz.aliyun.com/news/18995)

### PTE Walk

说白点就是扫描内存4级页表, 如上面​`KdMapper`的逻辑最后的内存至少是可读可执行, 也就是PTE.Nx位必须为0, 我们遍历页表记录这种PTE连续且规模巨大的可读执行内存, 最后配合内存特征就能快速定位.

### NMI

就是通过Nmi不可屏蔽中断打断线程流程, 执行我们的堆栈检查回调, 判断当前线程Rip是否在正常模块地址区间

```c
KeRegisterNmiCallback(NmiCallback, g_NmiContext);
```

[https://bbs.kanxue.com/thread-288576.htm](https://bbs.kanxue.com/thread-288576.htm)

### .data ptr hijack

有些恶意驱动会劫持某个Nt系列函数进行通信, 这个时候我们通过SSDT HOOK的方式来监控Nt系列函数调用流程, 检测异常高频调用, 像NtUserCreateWindowStation\NtReadFile\NtWriteFile 这类重灾区函数.

至于SSDT HOOK的实现可以使用infinityHook、Pte Page Hook、Ept Hook、lstar Msr Hook等等方式.
